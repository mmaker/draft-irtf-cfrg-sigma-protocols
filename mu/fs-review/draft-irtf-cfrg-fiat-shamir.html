Fiat-Shamir Transformation

Abstract

This document describes the Fiat-Shamir transformation, which allows making a public-coin protocol non-interactive by means of a cryptographic hash function.¶

It specifies how the hash function is employed, how prover messages are encoded as hash-function input, and how verifier messages are decoded from the hash function's output, as well as the serialization and deserialization of the non-interactive argument string.¶

1. Introduction

A public-coin interactive protocol is an exchange of messages between a prover and a verifier in which every verifier message is a uniformly random value sampled independently of the protocol state. The Fiat-Shamir transformation removes interaction from a public-coin interactive argument by relying on a cryptographic hash function. The non-interactive prover derives each verifier message on its own via a hash function, and serializes the protocol transcript into a non-interactive argument (NARG) string. The verifier recomputes the same verifier messages from the NARG string and checks the interactive verifier's decision. The resulting argument is secure in the random oracle model.¶

This document describes the duplex sponge Fiat-Shamir transformation, and in particular:¶

  • a non-interactive argument prover (NARG prover), and¶

  • a non-interactive argument verifier (NARG verifier)¶

The prover is a randomized procedure and generally relies on a cryptographically-secure entropy source; the verifier SHOULD be deterministic. Both the non-interactive prover and verifier rely on:¶

  • a duplex sponge, prescribing how to interact with the cryptographic hash function (Section 3);¶

  • a set of codecs, describing how each prover message is absorbed into the sponge and how each verifier message is derived (Section 4);¶

  • a serialization and deserialization procedure for the NARG string produced by the prover (Section 6).¶

This document specifies only byte-oriented hash functions, but this transformation generalizes to alphabets other than bytes (for example, prime-field elements); see [CO25] for the general construction.¶

Other types of non-interactive transformations (with and without random oracles) are possible, but outside the scope of this specification.¶

The security guarantees provided by this transformation are described in Section 7.¶

2. Terminology and conventions in this document

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

The following notation is used throughout this document.¶

2.1. Bytes and integers

A byte is an 8-bit unsigned integer (an octet), and a byte string is a finite sequence of bytes. An N-byte string is a byte string of length N. The empty byte string is written ""; x || y is the concatenation of the byte strings x and y. zeros(N) denotes the N-byte string of zero bytes.¶

I2OSP(n, w) and OS2IP(x) are the primitives defined in Section 4 of [RFC8017]. I2OSP(n, w) converts a non-negative integer n less than 256^w into a w-byte, big-endian byte string. OS2IP(x) converts a byte string x into a non-negative integer using the big-endian byte order.¶

A byte string x is a prefix of a byte string y if y == x || z for some byte string z (even empty). An encoding is prefix-free if, for any two distinct values, the encoding of one is never a prefix of the encoding of the other. A simple prefix-free encoding of a byte string b is I2OSP(len(b), 4) || b as described in Section 4.1.2.¶

2.2. Duplex sponge interface

The Fiat-Shamir transformation is built on a cryptographic hash function, modeled as a random oracle. Rather than computing a single fixed-length digest, this document uses the hash function through a stateful interface called a duplex sponge (defined in Section 3), which Absorbs prover messages into one evolving internal state and Squeezes from that state the bytes from which verifier challenges are derived. This interleaving is essential to the transformation: each verifier challenge must depend on every prover message absorbed before it.¶

The interface generalizes the sponge [SPONGE], which maps a variable-length input to a variable-length output by absorbing all of its input and then squeezing all of its output, to the duplex setting [DUPLEX], in which absorbing and squeezing may be arbitrarily interleaved over a single retained state. The state is split into a rate, the portion through which bytes are absorbed and squeezed, and a capacity, which is never read or written directly and whose size sets the security level. The instantiation in Section 3.2 realizes this interface on top of the standard sponge-based extendable-output function (XOF).¶

The squeezed bytes stand in for the verifier's random coins, so the security of the transformation rests on the capacity. The properties a concrete instantiation must satisfy for this to hold, and the resulting security loss, are given in Section 7 and analyzed in [CO25].¶

2.3. Proof systems terminology

A prover message is a message sent by the interactive prover, and a verifier message is a message sent by the interactive verifier (a uniformly random value, since the protocol is public-coin). A message can be a value of any type for which a codec (Section 4) is defined, such as a byte string, an unsigned integer, or a group element. The transcript is the ordered sequence of prover and verifier messages.¶

The instance specifies the statement being proven and is held by both the prover and the verifier.¶

The witness is the prover's private input. It is known only to the prover and is never revealed. It appears neither in the transcript nor in the NARG string.¶

For an NP relation, the instance is a word, the witness is its proof, and the resulting non-interactive argument proves that the instance is in the corresponding NP language. Proof systems might rely on different relations or express the same relation in different ways. The statement family denotes the relation whose membership is being proven.¶

The NARG string (non-interactive argument string) is the serialized output of the non-interactive prover.¶

The notation in this document is for an interactive argument with k rounds in which the prover moves first and the verifier moves last. Other types of interactions can be expressed in the same notation by setting the unused messages to the empty string: a protocol whose verifier moves first (such as a batch argument) sets its first prover message to "", and one whose prover moves last (such as a sigma protocol) sets its final verifier message to "".¶

2.4. Codec and serialization

A prover message is processed in two independent ways: it is absorbed into the hash function to derive the verifier's challenges, and it is written into the NARG string sent to the verifier. This document keeps the two separate.¶

A codec (Section 4) is the pair of maps between messages and the hash function's alphabet (bytes, in this document):¶

  • Encoding converts the instance and each prover message into the bytes absorbed by the sponge (Section 4.1).¶

  • Decoding converts the bytes squeezed from the sponge into a uniformly-distributed verifier message (Section 4.2).¶

Serialization (Section 6) is the pair of maps between prover messages and the NARG string:¶

  • Serialization writes the prover messages into the NARG string produced by the non-interactive prover.¶

  • Deserialization reads the prover messages back from the NARG string, and returns an error if the message is invalid.¶

For a prover message the serialized bytes coincide with the encoded bytes (Section 6.1), but the two serve different purposes: encoding is constrained for the security of the transformation (it is prefix-free), while deserialization is constrained to make parsing of the NARG string unambiguous (trailing or invalid byte strings are rejected).¶

3. Duplex sponge instantiations

This section lists the duplex sponge instantiations provided in this document.¶

3.1. Interface

Prover and verifier messages are handled via three operations:¶

  • Init(session_id) -> state: create a new duplex sponge state, seeded by the 32-byte domain-separation string session_id.¶

  • Absorb(x): absorb the byte string x into the state.¶

  • Squeeze(n) -> buf: produce n bytes from the state.¶

Messages can be absorbed incrementally: Absorb(x) followed by Absorb(y) is equivalent to Absorb(x || y). The output of Squeeze(n) is uniformly distributed over n-byte strings and depends on the session identifier and on every byte absorbed before the call. Guidance on how to produce a 32-byte session_id is given in Section 5.1; the security properties an instantiation must provide are specified in Section 7.8.¶

3.2. SHAKE128 duplex sponge

SHAKE128 [SHA3] is used as a duplex sponge over the Keccak-f[1600] permutation. The state is a 200-byte (1600-bit) string, split into a rate of R = 168 bytes and a capacity of 32 bytes.¶

3.2.1. Init

Seed the state by absorbing the session identifier, padded with zeros to fill the rate (the remaining R - 64 = 104 bytes).¶

Init(self, session_id)

Input: session_id, a byte array

Output: a duplex sponge state

1. assert len(session_id) == 64
2. ctx = SHAKE128.New()
3. ctx.Update(session_id || zeros(R - 64))
4. return state := (ctx, reader = None)
¶

3.2.2. Absorb

Feed a byte string x into the state.¶

Absorb(state, x)

Inputs:

- state, a duplex sponge state
- x, a byte array

1. state.reader = None
2. state.ctx.Update(x)
¶

3.2.3. Squeeze

Returns the next n bytes of the SHAKE128 output stream computed over the absorbed input. If the sponge is in the absorbing phase, it finalizes a copy of the absorbing context as a SHAKE128 XOF reader. Consecutive Squeeze calls continue the same SHAKE128 output stream.¶

Squeeze(state, n)

Inputs:

- state, the duplex sponge state
- n, the number of elements to be squeezed

Output: a uniformly-distributed random n-byte string

1. if state.reader == None:
2.    state.reader = self.ctx.Copy().Finalize()
3. state.reader.read(n)
¶

4. Codecs

A codec is a set of functions that map prover and verifier messages to the hash function's alphabet:¶

  • Encoding converts prover messages into the bytes absorbed by the sponge. Encoding functions MUST be prefix-free.¶

  • Decoding converts squeezed bytes into verifier messages. Decoding MUST preserve the uniform distribution (up to a small codec error).¶

Codecs serve a different purpose than proof serialization, which is described in Section 6.1.¶

4.1. Encoding into byte strings

All encoding functions MUST be prefix-free.¶

4.1.1. Byte strings

The encoding of a non-empty byte string is the identity map. The caller is responsible for ensuring that the length is fixed by the surrounding protocol.¶

EncodeBytes(x)

Input: x, a non-empty N-byte string

Output: out, a N-byte string

1. return x
¶

4.1.2. Variable-length byte strings

A byte string of fewer than 2^32 bytes is encoded as its byte length (via I2OSP), followed by its bytes. The length prefix makes the encoding prefix-free.¶

EncodeString(s)

Input: s, a N-byte string

Output: out, a (N+4)-byte string

1. return I2OSP(len(s), 4) || b
¶

4.1.3. Sequences and tuples

A fixed-length array or a tuple is encoded as the concatenation of the encodings of its elements, with no separators.¶

4.1.4. Unsigned integers

An integer modulo M is represented by its unique integer representative in the range [0, M) and encoded big-endian as defined in I2OSP [RFC8017].¶

EncodeScalar(x, M)

Inputs:
- x, an integer modulo M
- M, the order of the integer ring

Output: out, a Ns-byte string

1. Ns = ceil(log2(M) / 8)
2. assert 0 <= x < M
3. return I2OSP(x, Ns)
¶

4.1.5. Elliptic curve groups

A scalar field element is serialized to a canonical Ns-byte string using the group's scalar field serialization function. For most prime-order elliptic-curve groups, this is equivalent to EncodeScalar described in Section 4.1.4.¶

A group element is serialized to a canonical Ne-byte string using the group's element-serialization function. For most prime-order elliptic-curve groups, this is the compressed Elliptic-Curve-Point-to-Octet-String conversion of [SEC1]. Each group element has exactly one Ne-byte representation. The value of Ne and the concrete conversion are fixed by the ciphersuite.¶

4.2. Decoding from byte strings

Decoding converts a uniformly-distributed Squeeze output into a verifier message. Each verifier message type fixes the number of bytes to squeeze.¶

Decoding is not serialization, and need not be injective; the requirement is that it be distribution-preserving: if its input is a uniformly random byte string, then its output is (statistically close to) uniformly distributed over the verifier message type.¶

4.2.1. Byte arrays

The decoding function for fixed-length byte arrays is the identity.¶

DecodeBytes(buf, N)

Inputs:
- buf, a byte string
- N, the expected byte length

Output: out, a byte string of length N

1. assert len(buf) == N
2. return buf
¶

4.2.2. Unsigned integers

To sample a uniformly random element modulo M of Ns bytes (that is Ns = ceil(log2(M) / 8)), decode Ns + 32 bytes by interpreting them as a big-endian non-negative integer with OS2IP, and reduce modulo M.¶

DecodeScalar(buf, M)

Inputs:
- buf, a byte string of length Ns + 32
- M, the modulus

Output: out, an integer in the range [0, M)

1. assert len(buf) == Ns + 32
2. return OS2IP(buf) mod M
¶

The 32 extra bytes (256 bits) ensure that the statistical distance between the reduced value and the uniform distribution over [0, M) is at most 2^-256, which is cryptographically negligible. More in general, sampling n bounds the bias by at least 2^-n.¶

In two cases this approach is inefficient: if log2(M) is significantly smaller than 256, and if M is a 2-power. In such cases, applications MAY use an alternative decoding function, provided it meets the following security requirements:¶

  • The function MUST have bias less than the soundness error of the interactive argument.¶

  • The function MUST NOT use rejection sampling.¶

  • The function SHOULD be amenable to straight-line implementations.¶

Similar requirements and a longer discussion are available in [RFC9380], Section 5.¶

5. Initialization

Before any prover message is processed, both parties start the duplex sponge with: the session identifier (Section 5.1), and then the instance (Section 5.3).¶

Neither input is carried in the NARG string: the verifier holds both as its own inputs and recomputes this prefix to re-derive the verifier challenges.¶

5.1. Session identifiers

The session identifier is a (non-zero) 32-byte string that identifies the application context.¶

For a duplex sponge operating over bytes, the following procedure DeriveSessionID allows to produce a secure session identifier provided the input tag satisfies the following security requirements:¶

  1. the tag MUST uniquely identify the non-interactive argument used, including the IP (interactive protocol), the types of prover and verifier messages, the hash suite, the statement family of the interactive argument, and the codecs used.¶

  2. the tag MUST contain contextual information about where the proof is made (e.g. a URL, or a timestamp).¶

  3. the tag SHOULD begin with a fixed identification string that is unique to the application.¶

  4. the tag SHOULD include a version number.¶

DeriveSessionID(tag)

Inputs:
- tag, an application-chosen byte string

Output: session_id, a non-zero 32-byte string

1. duplex_sponge = DS.Init("irtf-cfrg-fiat-shamir/session-id")
2. duplex_sponge.Absorb(tag)
3. return duplex_sponge.Squeeze(32)
¶

The 32-byte label "irtf-cfrg-fiat-shamir/session-id" is a 32-byte string for domain separation in this derivation.¶

As an example, consider a fictional application named Foo that implements sigma protocols over elliptic curves for encrypted messages shared during a time epoch tt. A reasonable choice of tag is FOO-SV{xx}-{tt}-DSFS-{hashID}-SIGMA-PROOFS-{yy}, where xx is the two-digit number indicating the version, yy is the two-digit number indicating the elliptic-curve ciphersuite, hashID is the hash identifier, and tt is the epoch identifier.¶

As another example, consider a fictional application named Bar that implements an ad-hoc zero-knowledge virtual machine for correct execution of circuits. A reasonable choice of tag is BAR-COM{cc} where {cc} is the commit hash of the associated version of the cryptographic specification of the protocol.¶

The procedure DeriveSessionID SHOULD be preferred over custom session identifiers, described in the next section.¶

5.2. Custom session identifiers

Applications MAY instead supply a session identifier directly.¶

A custom session identifier MUST consist of at least 32 zero bytes followed by a non-empty tag, and should not exceed R bytes.¶

session_id = zeros(32)
¶

The leading 32 zero bytes domain-separate custom identifiers from the ones specified in the previous section.¶

Applications needing a label longer than R - 32 bytes SHOULD derive instead.¶

5.3. Instance

The instance is the public input that fixes the specific statement being proven, within the statement family identified by the session identifier.¶

The prover and verifier MUST include the instance immediately after Init(session_id), and before any prover message.¶

The encoding map encode[0] MUST be prefix-free, and and SHOULD reuse the encodings of Section 4.1.¶

Omitting public statement data from the sponge compromises soundness of the proof system. See Section 7.8.1.¶

6. Non-interactive argument string

6.1. Serialization

Serialization is the concatenation of the byte encoding of each prover message, as defined in Section 4.1.¶

6.2. Deserialization

Deserialization of the NARG string consists in reading the prover messages and computing the inverse of the serialization procedure: each message is read by consuming a fixed number of bytes, determined by its type and the instance, and advancing past them.¶

Verification MUST fail if any of the prover messages cannot be deserialized successfully. After the last expected prover message has been read, the verifier MUST verify that no bytes remain. Bytes that are never read or that are decoded despite being invalid will defeat strong simulation extractability: an adversary will be able to malleate a valid proof to obtain a second, distinct accepting proof for the same statement.¶

6.2.1. Byte strings

Read the next N bytes, where N is fixed by the protocol, and return them. Any N-byte string is a valid encoding.¶

6.2.2. Character strings

Read a 4-byte length N via OS2IP, then read the next N bytes. Fail if fewer than N bytes remain, or if those bytes are not a valid UTF-8 encoding. The value is the resulting string.¶

DeserializeString(input)

Input: input, the unread remainder of the NARG string

Output: s, a UTF-8 string

1. assert len(input) >= 4
2. N = OS2IP(input[0:4])
3. assert len(input) == 4 + N
4. b = input[4 : 4 + N]
5. return utf8_decode(b)
¶

This consumes 4 + N bytes of the NARG string.¶

6.2.3. Sequences and tuples

Deserialize each element in order. Fail if any element fails to deserialize. The number and types of the elements are fixed by the protocol.¶

6.2.4. Unsigned integers

Read the next Ns bytes and interpret them as a big-endian integer m = OS2IP(.). If m >= M, fail: non-canonical encodings of field elements MUST be rejected. The value returned is m.¶

6.2.5. Group elements

Read the next Ne bytes and convert them to a group element using the group's element-deserialization function.¶

For the elliptic-curve groups in scope, this is the decoding procedure — for example, the Octet-String-to-Elliptic-Curve-Point conversion of [SEC1]. Deserialization MUST perform the ciphersuite's input-validation steps and fail unless the input is the canonical encoding of a valid group element.¶

For elliptic curves, these steps check that the coordinates are in the correct range and that the point lies in the subgroup used for cryptographic operations.¶

7. Security Considerations

This section contains additional security considerations about the Fiat-Shamir transformation as described in this document.¶

7.1. Properties of codecs

Encoding and decoding maps MUST be infallible. Batch encoding/decoding algorithms should be preferred when available.¶

While encoding maps are never inverted, the security proof relies on a left inverse existing and being efficiently computable when building the extractor for knowledge soundness.¶

It is also easy to see that using a non-uniform input produces an output that is easily distinguished from a uniformly random point.¶

7.2. Constant-time requirements

Constant-time implementation of all the functions in this document is strongly RECOMMENDED, to avoid leaking information via side channels. While the protocol operates on "public coins", the instance can contain private information, such as verification keys not meant to be shared, or messages meant to be private between prover and verifier.¶

For example, in the case of keyed-verification anonymous credentials, the zero-knowledge verifier will compute an instance that depends on the issuer's secret key and as such the instance is not meant to be public.¶

7.3. Session identifiers

The purpose of session identifiers is to ensure composability and mitigate protocol confusion.¶

7.4. Security of the transformation

The Fiat-Shamir transformation carries over the soundness and zero-knowledge properties of the interactive proof.¶

Completeness of the non-interactive argument is preserved: if the statement being proven is true, then the resulting non-interactive argument string is valid.¶

7.5. Soundness

If the interactive proof is sound, then so is the non-interactive proof. In particular, valid proofs cannot be generated without possession of the corresponding witness (in the random oracle model).¶

Soundness and straight-line knowledge soundness carry over to the non-interactive argument, with an additive soundness loss quadratic in the number of queries the adversary makes to the random oracle [CO25].¶

7.6. Zero-Knowledge

If the interactive proof is honest-verifier zero-knowledge, then so is the non-interactive proof. In particular, the resulting argument string does not reveal any information beyond what can be directly inferred from the statement being valid.¶

The additive zero-knowledge loss introduced by the transformation is linear in the number of queries the adversary makes to the random oracle [CO25].¶

7.7. Quantum adversaries

If the interactive proof is sound against quantum adversaries, then the non-interactive proof after the Fiat-Shamir transformation in the random oracle model is also secure against quantum adversaries.¶

The loss introduced by a quantum adversary is polynomial (larger than quadratic) in the number of quantum random-oracle queries.¶

7.8. Indifferentiability of the hash function

The random oracle instantiation MUST be extraction-friendly and simulation-friendly indifferentiable to preserve soundness and zero-knowledge of the transformation.¶

To provide soundness and zero-knowledge, stronger capabilities than indifferentiability are needed [CO25]. Implementers do not need these notions to use the transformation, but they are the reason a different hash construction SHOULD NOT be substituted on the strength of indifferentiability alone.¶

7.8.1. Instance encoding

Instance encoding.¶

7.9. Implementation guidance

The Fiat-Shamir transformation has historically led to a number of critical security vulnerabilities, especially due to incorrect implementations involving out-of-order, or missing prover messages.¶

Absorbing a prover message and serializing it to (or reading it from) the NARG string SHOULD be coupled, to prevent prover messages from being hashed without being serialized, or from being skipped or reordered.¶

A sequential transcript interface is RECOMMENDED: implementations are encouraged to expose two directed state machines¶

  • (instance, witness) -> prove -> proof, and¶

  • (instance, proof) -> verify -> accept/reject¶

where prover messages are randomly addressable.¶

APIs exposing a proof object are prone to soundness bugs, as they provide out-of-order or partial access to prover messages. A byte-oriented stream enforces sequential, exactly-once processing. An end-of-input check is necessary to prevent malleability pitfalls.¶
