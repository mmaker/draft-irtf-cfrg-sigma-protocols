Sigma Proofs for Linear Relations

Abstract

This document describes Sigma Protocols for proving knowledge of pre-images of linear maps in prime-order elliptic curve groups. Examples include zero-knowledge proofs for discrete logarithm relations, ElGamal encryptions, Pedersen commitments, and range proofs.¶

1. Introduction

Zero-knowledge proofs of knowledge allow a prover to convince a verifier that a statement is true, without revealing anything else than what is already revealed by the statment itself. Many practically-relevant statements about discrete logarithm relations can be realized using so-called Sigma Protocols. Introduced by Schnorr [RFC8235] over thirty years ago, they are now widely used in practice because of their simplicity, maturity, and versatility.¶

Sigma Protocols are an essential component of a number of cryptographic constructions, such as anonymous credentials [ARC] [BBS], verifiable random functions [RFC9381], anonymous tokens [RFC9497], ring and blind signatures [BBSBlind], and proofs of knowledge of the opening of a Pedersen commitment [Pedersen91]. This document specifies a single Sigma Protocol for proving knowledge of a preimage of a linear map over a prime-order group [Cramer97] [Maurer09].¶

A Sigma Protocol is an interactive proof with the following three-message flow:¶

The messages are respectively called commitment (computed by the prover), challenge (randomly sampled by the verifier), and response (computed by the prover). The challenge is a scalar drawn uniformly at random from the scalar field of order p; in the interactive protocol the verifier samples it directly (Section 2.2), while non-interactive deployments derive it deterministically from the transcript via compute_challenge (Section 5), and its serialization is the canonical fixed-length scalar encoding of Section 2.3.2. The prover is stateful and maintains a single-use private state between the first and third messages. The public transcript, checked by the verifier, is (commitment, challenge, response). Sigma Protocols can compose: several statements can be proven simultaneously (AND composition), disjunctively (OR composition [CramerDS94]), or thresholded. AND composition of linear relations is immediate in this document (Section 4.3); OR and threshold composition, and composition across heterogeneous proof systems, are more delicate and carry soundness and zero-knowledge caveats -- see Section 7 and Section 7.4.¶

This document fixes the interface for Sigma Protocols, and then focuses on discrete-logarithm relations that can be expressed as the preimage of a linear morphism. Affine relations with constant terms, or quadratic equations, can still be reduced to this form (Section 4).¶

The following notation is used throughout this document.¶

2.1. Bytes and integers

A byte is an 8-bit unsigned integer (an octet), and a byte string is a finite sequence of bytes. The empty byte string is written "", x || y is the concatenation of the byte strings x and y, and len(x) is the length of x in bytes. Byte strings are indexed from zero: for integers 0 <= i <= j <= len(x), x[i : j] denotes the (j - i)-byte substring of x at positions i, i+1, ..., j-1, so that x[0 : N] is the first N bytes of x and x[i : i] is "".¶

I2OSP(n, w) and OS2IP(x) are the integer/byte-string conversion primitives used throughout this document, in big-endian byte order, as defined in Section 4 of [RFC8017]. I2OSP(n, w) converts a non-negative integer n with 0 <= n < 256^w into a w-byte, big-endian byte string, and fails if n >= 256^w; OS2IP(x) is its inverse, mapping a w-byte string to the integer in [0, 256^w) that it represents. Byte order and length of the scalar and group-element encodings are fixed by each ciphersuite (Section 8).¶

2.2. Randomized algorithms

Prover algorithms that require fresh randomness take as input a cryptographically secure random number generator, denoted rng. This document uses rng.random_scalar() to denote sampling a uniformly random element of the scalar field. Sampling a random scalar takes two steps: obtaining high-quality entropy from the operating system's CSPRNG (e.g., getrandom() [RFC4086]), and reducing the resulting bytes to a scalar, as described for DecodeField in [fiat-shamir].¶

2.3. Group abstraction

Elliptic curves are presented using additive notation.¶

In symbolic notation, group elements are written upper-case (G, X, M) and scalars lower-case (x, s). Pseudocode and interface names are descriptive (e.g. commitment, image, witness) and do not follow this rule.¶

2.3.1. Group

identity() is the neutral element, generator() fixes the generator of the prime-order subgroup, and order() returns its order p. Addition, equality, and scalar multiplication by a Scalar are written +, ==, and * (via operator overloading, in place of add, equal, scalar_mul).¶

serialize(elements: [Group; N]) and deserialize(buffer) convert N non-neutral group elements into fixed-length Ne * N-byte encoding, where Ne is fixed per ciphersuite (Section 8). Deserialization must raise an error in case of failure.¶

2.3.2. Scalar

identity() is the additive identity of the scalar field. Addition and multiplication are written + and * (via operator overloading, in place of add, mul). random(rng) samples a scalar from rng, decoding bytes as described for random in the unsigned-integer decoding of [fiat-shamir].¶

serialize(scalars: list[Scalar; N]) and deserialize(buffer) batch convert between [Scalar; N] and its canonical, fixed-length Ns * N-byte encoding.¶

3. Interface

A sigma protocol provides the following interface:¶

  • ProverCommitment(instance, witness, rng): produces a pair (commitment, prover_state) consisting of the public prover message, the commitment, and a private prover_state. The prover state is meant to be used only once per proof. The random number generator rng is defined in Section 2.2.¶

  • ProverResponse(prover_state, challenge) produces the response.¶

  • Verifier(instance, commitment, challenge, response), the verification algorithm.¶

These are the interactive protocol's building blocks: challenge above is whatever value the verifier supplies. They MUST NOT be invoked with a challenge that was not either sent by an honest interactive verifier or derived via compute_challenge (Section 5); supplying an arbitrary challenge instead skips the Fiat-Shamir transformation entirely (see Section 7.1). Non-interactive deployments call prove_batchable, verify_batchable, prove_compact, or verify_compact (Section 5) rather than these functions directly.¶

Implementations MAY also provide the zero-knowledge simulator:¶

  • SimulateResponse(instance, rng), which returns a simulated_response, a vector of scalars distributed as an honest response would be.¶

  • SimulateCommitment(instance, response, challenge), which returns the simulated_commitment consistent with that response and challenge.¶

Both are specified concretely for the linear-map Sigma Protocol in Section 4.7. The simulator is useful for proof composition (e.g. OR-composition [CramerDS94]) and for compact proof serialization ([BonehS23]).¶

4. Proofs of preimage of a linear map

This section specifies proofs of knowledge for the preimage of a linear map over a group, also known as preimage of a linear morphism, Maurer proofs [Maurer09], or Cramer proofs [Cramer97].¶

A linear map is a matrix-vector product M * witness = image, where M is a matrix of group elements, witness is a vector of scalars, and image is the vector of group elements obtained by scalar-multiplying and summing entries of M by witness, using the group operations of Section 2.3. The relation proven by this document is:¶

R := { (witness, image) : M * witness = image }
¶

or, expanded coordinate-wise:¶

image[i] = sum(witness[j] * M[i][j] for j in range(num_scalars))
           for i in range(num_equations)
¶

num_scalars is the number of scalars in witness (the width of M), and num_equations is the number of group elements in image (the height of M), i.e. one equation per output element. The witness is represented simply as an array of num_scalars scalars, Witness = [Scalar; num_scalars].¶

As an example, Schnorr's identification protocol has num_scalars = num_equations = 1 and M = [G.generator()], proving knowledge of x such that x * G.generator() = X [RFC8235].¶

Another example is the Chaum-Pedersen relation [ChaumP92]: given group elements G, H, X, Y, the prover shows knowledge of a single scalar x such that X = x * G and Y = x * H. Here num_scalars = 1, num_equations = 2, and:¶

M = [[G],
     [H]]
¶

Variants of the Chaum-Pedersen relation are widely used for VRFs [RFC9381] and anonymous tokens [RFC9497]. Proving knowledge of the opening (m, r) of a Pedersen commitment [Pedersen91] C = m * G + r * H is the representation-proof case [Okamoto92]: a single equation of two terms, with num_scalars = 2. More elaborate relations (affine equations with constant terms, quadratic equations, and, by extension, any arithmetic circuit) reduce to this same form.¶

The group elements and the shape of the matrix depend on the statement being proven, and constructing the wrong matrix leads to bugs. For the relation to be meaningful, the group elements combined in each equation must have no known discrete-logarithm relation among them; otherwise the statement might be trivial. For instance, x * G + y * 5G] has p valid witnesses, and given it's easy to solve without. Generating such elements is the responsibility of the proving system and requires care; one way is to hash to the curve (Section 3 of [RFC9380]).¶

4.1. Linear map

Matrices M arising from these relations are typically sparse: both examples above have a single nonzero entry per row. This document therefore handles and serializes them in Yale/CSR sparse-matrix format, rather than as an array of group elements.¶

4.2. Representation

An Equation is one row of M: a non-empty list of (scalar_index, element_index) pairs giving the terms summed on its right-hand side.¶

A LinearRelation holds a set of group elements (each corresponding to an element_index), a non-empty list of equations, and the image outputs (e.g. X, Y).¶

class Equation:
    terms: list[(int, int)]     # (scalar_index, element_index) pairs; non-empty

class LinearRelation:
    Group: groups.Group
    elements: list[Group]; non-empty
    equations: list[Equation]   # one row per equation; non-empty
    image: list[int]            # image of the linear map
¶

A LinearRelation MUST have at least one equation, and every equation's terms MUST be non-empty: a relation with zero equations proves nothing, and a zero-term equation would assert only that some pool element equals identity(), a case this document assigns no meaning to. len(image) == len(equations), and every group element of elements MUST be set (Section 2.3) before the relation is used.¶

The following quantities are derived from a LinearRelation:¶

num_elements(relation)  = len(relation.elements)
num_equations(relation) = len(relation.equations)
num_scalars(relation)   = 1 + max(s for eq in relation.equations
                                    for (s, _) in eq.terms)
¶

Note that num_elements, the size of the group-elements set, is independent from num_equations. For instance, in Chaum-Pedersen, num_elements = 4 (G, H, X, Y), while num_equations = 2.¶

This document writes map(relation, scalars) for the function that evaluates M at scalars:¶

map(relation, scalars) -> list[Group]

1. image = []
2. for equation in relation.equations:
3.     acc = relation.Group.identity()
4.     for (scalar_index, element_index) in equation.terms:
5.         acc = acc + scalars[scalar_index] * relation.elements[element_index]
6.     image.append(acc)
7. return image
¶

4.3. Specifying a linear relation

This section defines a symbolic notation for declaring scalars, elements, and equations in the notation of [CamenischS97], together with the deterministic rule that compiles a declaration into the indexed LinearRelation of Section 4.2.¶

A relation is declared as a named block, parameterized by the concrete element values it will be instantiated with, so that it is written once and referenced by name wherever it is used -- in particular, identically by the prover and the verifier, which always agree on the instance:¶

Relation NAME(params...):
    Scalars: s[0], ..., s[k-1]
    Elements: E[0], ..., E[n-1]
    Equations:
        E[i] = <linear combination of scalars and elements>
        ...
¶

Scalars: and Elements: each list names in the order the compiled LinearRelation assigns them indices: the j-th name under Scalars: becomes scalar index j, and the j-th name under Elements: becomes relation.elements[j] (Section 4.2). The named parameters are matched by name against the Elements: entries and substituted with the concrete element values supplied at instantiation.¶

A loop over an index variable (for example, declaring D_0, ..., D_{n-1} with one equation per i) expands in the order the loop executes, before names are assigned indices.¶

For example, the Chaum-Pedersen relation of Section 4 is declared as:¶

Relation ChaumPedersen(G, H, X, Y):
    Scalars: x
    Elements: G, H, X, Y
    Equations:
        X = x * G
        Y = x * H
¶

which compiles to the LinearRelation with elements = [G, H, X, Y], equations = [Equation(terms=[(0, 0)]), Equation(terms=[(0, 1)])], and image = [2, 3].¶

Each line of Equations: has the form element_name = term + term + ..., where each term is scalar_name * element_name; it compiles to one Equation of Section 4.2 whose terms are the (scalar_index, element_index) pairs of its right-hand side, in the order written, and whose image index is the pool index of the left-hand-side element.¶

Both lists MUST enumerate every name used in Equations:, and MUST NOT repeat a name. Terms MUST be less than 2^32. Every term MUST be a single scalar_name * element_name product: the notation has no constant terms, no scalar-scalar or element-element products, and no affine offsets. A constant base is expressed as an Elements: entry multiplied by a scalar fixed to 1; affine and quadratic statements reduce to this product form as described in Section 4.¶

Because a LinearRelation may hold any number of equations over shared or disjoint variables, AND composition -- proving several relations simultaneously -- comes for free: concatenate the Scalars:, Elements:, and Equations: of each sub-relation (renaming any clashing names) into a single declaration and compile it as one LinearRelation, which binds every sub-statement under a single challenge (Section 5).¶

A Relation NAME(params...) declaration desugars to a function NAME(...) returning the compiled LinearRelation, with the named parameters substituted for the matching Elements: entries. The prover computes the concrete element values and calls NAME(...) to obtain the instance passed to prove_batchable or prove_compact (Section 5); the verifier calls the same NAME(...) with the element values it independently holds (public keys, ciphertexts, or other values received from the prover) to obtain the identical instance passed to verify_batchable or verify_compact. This is the intended integration point for specifications built on this document: the definition of a statement is a Relation declaration, not a hand-written sequence of index-allocation calls.¶

Some element values are not fixed public parameters but are chosen by the prover and supplied to the verifier -- for instance, rerandomized bases or commitments computed per proof. Such prover-supplied elements are part of the instance, not of the NARG string (Section 5.1): they travel to the verifier outside the proof bytes (which carry only commitment and response), and the verifier substitutes the received values into NAME(...) to reconstruct the instance before calling verify_batchable or verify_compact. Because the challenge is computed over the serialized instance (Section 4.4), any modification of these values changes the challenge and the proof fails; this is what binds them to the proof, and it is also why prover and verifier MUST agree on the instance (Section 5). Being attacker-controlled input, each prover-supplied element MUST pass the same deserialization validation as any untrusted group element (Section 2.3, Section 7.1) before it is used.¶

4.4. Serialization

A LinearRelation is serialized as a sparse matrix in row-major order, followed by the group elements set. Each row is serialized encoding the number of non-zero entries (in 4 bytes, via I2OSP Section 2.1), followed by the indices pair (scalar index, element index) for each entry (Section 4.2). The group elements are serialized using the group serialization function.¶

SerializeLinearRelation(relation)

Input:

- relation, a linear relation.

Output:

- a byte string

Procedure:

 1. out = ""
 2. out = out || I2OSP(num_equations(relation), 4)
 3. for i in range(num_equations(relation)):
 4.     out = out || I2OSP(relation.image[i], 4)
 5.     terms = relation.equations[i].terms
 6.     out = out || I2OSP(len(terms), 4)
 7.     for (scalar_index, element_index) in terms:
 8.         out = out || I2OSP(scalar_index, 4)
 9.         out = out || I2OSP(element_index, 4)
10. return out || Group.serialize(relation.elements)
¶

Here relation.image[i] is the pool index of the output element of the i-th equation (Section 4.2), and each right-hand side term (scalar_index, element_index) pairs a scalar (witness) index (Section 4, Paragraph 6) with a group-element index.¶

The encoding binds the entire statement: the shape of the linear map (the number of equations and the indices wired into each one) together with every group element of the instance. Because num_equations(relation) >= 1 and every equation has at least one term (Section 4.2), the output is always non-empty. For a fixed relation the output has a fixed length, so it is prefix-free, as required of the instance encoding by [fiat-shamir].¶

4.5. Prover

The prover of a Sigma Protocol is stateful and will send two messages, a "commitment" and a "response" message, described below.¶

4.5.1. Prover commitment 

ProverCommitment(instance, witness, rng)

Inputs:

- instance, the LinearRelation being proven
- witness, an array of scalars
- rng, a cryptographically secure random number generator

Outputs:

- A (private) prover state
- A commitment message (a vector of group elements).

Procedure:

1. nonces = [rng.random_scalar() for _ in range(num_scalars(instance))
2. commitment = map(instance, nonces)
3. return (prover_state := (witness, nonces), commitment)
¶

4.5.2. Response 

ProverResponse(prover_state, challenge)

Inputs:

    - prover_state, the current state of the prover
    - challenge, the verifier challenge scalar

Outputs:

    - An array of scalar elements composing the response

Procedure:

1. witness, nonces = prover_state
2. return [nonces[i] + witness[i] * challenge for i in range(len(nonces))]
¶

4.6. Verifier 

Verifier(instance, commitment, challenge, response)

Inputs:

- instance, the LinearRelation being verified
- commitment, the commitment generated by the prover
- challenge, the challenge generated by the verifier
- response, the response generated by the prover

Outputs:

- A boolean indicating whether the verification succeeded

Procedure:

1. assert len(commitment) == num_equations(instance) and \
2.        len(response) == num_scalars(instance)
2. expected = map(instance, response)
3. image = [instance.elements[i] for i in instance.image]
4. got = [commitment[i] + image[i] * challenge for i in range(num_equations(instance))]
5. return got == expected
¶

4.7. Simulator

Implementations that expose the zero-knowledge simulator (Section 3) provide the two algorithms below; they are also what the compact verifier (Section 5) relies on to recover the prover's commitment from (challenge, response).¶

The simulator rearranges the verification equation of Section 4.6: an accepting transcript satisfies commitment[i] + image[i] * challenge == map(instance, response)[i] for every equation i, so the commitment determined by a response and a challenge is map(instance, response) - challenge * image.¶

SimulateResponse(instance, rng)

Inputs:

- instance, the LinearRelation
- rng, a cryptographically secure random number generator ({{rng-definition}})

Outputs:

- response, a simulated response: a vector of num_scalars(instance) scalars

Procedure:

1. return [rng.random_scalar() for _ in range(num_scalars(instance))]
¶ 
SimulateCommitment(instance, response, challenge)

Inputs:

- instance, the LinearRelation
- response, a vector of num_scalars(instance) scalars
- challenge, a challenge scalar

Outputs:

- commitment, a vector of num_equations(instance) group elements

Procedure:

1. expected = map(instance, response)
2. image = [instance.elements[i] for i in instance.image]
3. return [expected[i] - challenge * image[i] for i in range(num_equations(instance))]
¶

Drawing response uniformly at random with SimulateResponse and then computing commitment with SimulateCommitment yields a transcript (commitment, challenge, response) identically distributed to an honest one, which is the honest-verifier zero-knowledge property (Section 7): an honest response nonces + witness * challenge is uniform because nonces is uniform, and the honest commitment map(instance, nonces) equals map(instance, response) - challenge * image.¶

5. Non-interactive Sigma Protocols

The Fiat-Shamir transformation applied to Sigma Protocols yields a non-interactive zero-knowledge argument of knowledge.¶

[fiat-shamir] describes how to instantiate the transformation, for the group and field codecs given.The security requirements of the session identifier session_id are discussed in Section 5.5. The actual choices of DecodeField are discussed in Section 8. Two serializations are possible.¶

5.1. Non-interactive argument string serialization

Two serialization flavors are possible:¶

  • A batchable NARG string serializes the prover messages (commitment, response), as in [fiat-shamir], and it permits batch verification of several proofs at once.¶

  • A compact NARG string serializes (challenge, response). It is preferable in the common cases, and whenever the commitment (num_equations group elements) is larger than a single challenge scalar.¶

A batchable NARG string is a (Ne * num_equations + Ns * num_scalars)-byte string, while a compact narg string is a (Ns * (num_scalars + 1))-byte string.¶

5.2. Computing the challenge

Both serializations below derive the verifier's challenge identically from the tag, the instance, and the prover's commitment. Let Ne and Ns be the element and scalar byte lengths of the ciphersuite (Section 8).¶

compute_challenge(tag, instance, commitment)

Inputs:

- tag, a byte string uniquely identifying the session
- instance, the LinearRelation being proven
- commitment, the prover's commitment message

Outputs:

- challenge, the verifier's challenge scalar

Procedure:

1. session_id = DeriveSessionID(tag)
2. duplex_sponge = DS.Init(session_id)
3. duplex_sponge.Absorb(SerializeLinearRelation(instance))
4. duplex_sponge.Absorb(Group.serialize(commitment))
5. return DecodeField(duplex_sponge.Squeeze(Ns + 16), p, 1)
¶

SerializeLinearRelation(instance) above is encode[0](instance) in the notation of [fiat-shamir].¶

5.3. Batchable

A batchable NARG string is the generic transformation ([fiat-shamir]), consisting of the concatenation of the prover messages serialize(commitment) || serialize(response).¶

prove_batchable(tag, instance, witness, rng)

Inputs:

- tag, a byte string uniquely identifying the session
- instance, the LinearRelation to be proven
- witness, the prover's secret witness
- rng, a cryptographically secure random number generator ({{rng-definition}})

Outputs:

- the batchable proof, a byte string

Procedure:

1. (commitment, prover_state) = ProverCommitment(instance, witness, rng)
2. challenge = compute_challenge(tag, instance, commitment)
3. response = ProverResponse(prover_state, challenge)
4. return Group.serialize(commitment) || Scalar.serialize(response)
¶ 
verify_batchable(tag, instance, proof)

Inputs:

- tag, a byte string uniquely identifying the session
- instance, the LinearRelation to be proven
- proof, the batchable proof byte string

Outputs:

- a boolean indicating whether the proof is valid

Procedure:

1. Nc = num_equations(instance) * Ne
2. Nr = num_scalars(instance) * Ns
3. fail if len(proof) != Nc + Nr
4. commitment = Group.deserialize(proof[0 : Nc])
5. response = Scalar.deserialize(proof[Nc : Nc + Nr])
6. challenge = compute_challenge(tag, instance, commitment)
7. return Verifier(instance, commitment, challenge, response)
¶

5.4. Compact

A compact proof serializes serialize(challenge) || serialize(response). The Sigma Protocol transcript is recovered invoking the simulator.¶

prove_compact(tag, instance, witness, rng)

Inputs:

- tag, a byte string uniquely identifying the session
- instance, the LinearRelation to be proven
- witness, the prover's secret witness
- rng, a cryptographically secure random number generator ({{rng-definition}})

Outputs:

- the compact proof, a byte string

Procedure:

1. (commitment, prover_state) = ProverCommitment(instance, witness, rng)
2. challenge = compute_challenge(tag, instance, commitment)
3. response = ProverResponse(prover_state, challenge)
4. return Scalar.serialize([challenge])
          || Scalar.serialize(response)
¶

The verifier recomputes the commitment from the challenge and response via SimulateCommitment (Section 4.7), then recomputes the challenge from that commitment and accepts only if it matches the one in the proof.¶

verify_compact(tag, instance, proof)

Inputs:

- tag, a byte string uniquely identifying the session
- instance, the LinearRelation to be proven; it MUST be the same as the one used by the prover
- proof, the compact proof byte string

Outputs:

- a boolean indicating whether the proof is valid

Procedure:

1. Nch = Ns
2. Nr = num_scalars(instance) * Ns
3. fail if len(proof) != Nch + Nr
4. challenge = Scalar.deserialize(proof[0 : Nch])[0]
5. response = Scalar.deserialize(proof[Nch : Nch + Nr])
6. commitment = SimulateCommitment(instance, response, challenge)
7. expected_challenge = compute_challenge(tag, instance, commitment)
8. return challenge == expected_challenge
¶

Note that since the simulator always outputs valid proofs, there is no need to run the verifier in this case.¶

5.5. Tag and session identifier

The session identifier session_id is a 32-byte string. It SHOULD be derived from a string tag using DeriveSessionID of [fiat-shamir]. The prover and verifier initialize their duplex sponge state from it (Section 5).¶

The tag is a byte string following the security requirements on the session identifier in [fiat-shamir].¶

As an example, consider a fictional application named Foo. A reasonable choice of tag is:¶

FOO-{xx}-{tttt}-{flavor}-{hashID}-SIGMA-PROOFS-{yy}
¶

where xx is the two-digit number indicating the version, tttt is a 32-bit integer identifying the epoch, flavor is DSFS for a batchable proof or CMPT for a compact proof (Section 5.1), hashID is the hash identifier, and yy is the two-digit number indicating the elliptic-curve ciphersuite.¶

6. Efficiency Considerations

Implementations SHOULD evaluate map(instance, scalars) (Section 4.2) using a multi-scalar multiplication (MSM) algorithm for each equation, rather than computing and summing each term individually; this matters most for equations with many terms.¶

The verifier of Section 4.6 is specified as the equality map(instance, response) == commitment + challenge * image, evaluated as two separate vectors for clarity. Implementations MAY instead verify each equation i by checking that commitment[i] + challenge * image[i] - sum(response[j] * M[i][j] for j) is identity(), accumulating all terms in a single MSM per equation. This folds the challenge * image[i] scalar multiplication into the same MSM as the row terms, sharing its point doublings, and negation is free on these curves; the arithmetic is otherwise identical to the equality above.¶

As observed in the efficiency considerations of [fiat-shamir], DS.Init(session_id) followed by Absorb(encode[0](instance)) depends only on the tag and instance, not on the witness or randomness of any particular proof. Implementations that produce or verify many proofs for the same instance, as computed by compute_challenge (Section 5), can precompute and reuse the duplex sponge state resulting from these two steps across proofs.¶

7. Security Considerations

Interactive Sigma Protocols have the following properties:¶

  • Knowledge soundness: If the proof is valid, the prover must have knowledge of a secret witness satisfying the proof statement. This property ensures that valid proofs cannot be generated without possession of the corresponding witness. The Sigma Protocol of this document achieves this via special soundness [Cramer97] [Maurer09] [ChiesaY24].¶

  • Honest verifier zero-knowledge: The proof string produced by the prove function does not reveal any information beyond what can be directly inferred from the statement itself. This ensures that honest verifiers gain no knowledge about the witness [ChiesaY24].¶

  • Completeness: If the statement being proved is true, an honest verifier can be convinced of this fact by an honest prover via the proof.¶

  • Deniable: Because Interactive Sigma Protocols don't have transferable message authenticity, a third party (not the prover or verifier) cannot be convinced that the prover made the proof. This means that the Sigma Protocol interaction is not transferable as evidence to a third party [JakobssonSI96] [Pass03].¶

7.1. Fiat-Shamir transformation

In practice, Sigma Protocols are almost always deployed non-interactively via the Fiat-Shamir transformation (Section 5), so the security considerations of [fiat-shamir] apply also here. In particular:¶

  • Security level. The knowledge-soundness error is governed by the size of the challenge set, the full scalar field of order p, together with the random-oracle loss analyzed in [fiat-shamir].¶

  • Instance binding. Soundness holds only if the encoded instance binds the entire statement (Section 4.4); omitting any generator or image element is a weak Fiat-Shamir vulnerability.¶

  • Verifier input validation. The NARG string is untrusted input. Verifiers MUST check the proof length (no trailing bytes) and reject malformed encodings before performing any algebraic check. For group elements, deserialization MUST verify that each point is canonically encoded, lies on the curve, and lies in the prime-order group. In particular, the latter requires a subgroup-membership check when the group cofactor is greater than one (Section 2.3). For instance, skipping on-curve or subgroup check enables invalid-curve attacks [JagerSS15]; accepting non-canonical field elements [CVE-2022-23806]. The session identifier, the NARG string, and the instance are to be considered malicious inputs. For instance, invalid group parameters have previously caused bugs as in [CVE-2020-0601]. The identity element MUST be rejected wherever it appears: in any deserialized prover message, and in any instance element, including elements the verifier derives from prover-supplied values (Section 2.3). For scalars, deserialization MUST reject any value that is not the canonical representative in [0, p); failing to check that signature or response components are in range and nonzero is the validation-skip class behind [CVE-2022-21449], and admitting non-canonical encodings of the same value yields proof malleability [CVE-2024-42461]. For compact proofs, the verifier MUST recompute the challenge and compare it before accepting.¶

  • Prover randomness. Draw fresh nonces from rng for every proof. A nonce reused under two different challenges reveals the witness as (r1 - r2) / (c1 - c2) -- the failure behind well-known Schnorr and ECDSA key recoveries. Derive nonces deterministically only if every input affecting the challenge (tag, instance, commitment) is bound into the derivation (Section 3, [fiat-shamir]).¶

  • Post-quantum. The hardness of the proved relation rests on the discrete logarithm problem, so these proofs are not post-quantum sound; see Section 7.4.¶

7.2. Privacy Considerations

Interactive Sigma Protocols only guarantee zero-knowledge against honest verifiers (Section 7); a malicious verifier may extract information from the interaction, so this interactive setting SHOULD NOT be used where verifiers cannot be trusted. The non-interactive Fiat-Shamir transformation removes this restriction, yielding publicly verifiable (transferable) proofs that are statistically zero-knowledge.¶

7.3. Constant-Time Requirements

The prover's control flow and memory access patterns are typically influenced by the witness. All group and field operations over private inputs -- scalar multiplication, modular reduction, random-value generation, and so on -- MUST be constant-time to avoid side-channel leakage of the witness; in applications such as keyed-verification credentials, the verifier's operations require the same treatment.¶

Implementations MUST securely delete prover state as soon as it is no longer needed, and SHOULD minimize the lifetime of sensitive material (witness and instance), explicitly zeroize temporary buffers after proof generation, and reduce exposure in crash dumps, swap/page files, and diagnostic logging.¶

7.4. Post-Quantum Considerations

These proofs provide statistical zero-knowledge: witness-hiding holds even against a quantum adversary with unbounded computational power, so they remain suitable for privacy properties such as post-quantum anonymity, unlinkability, blindness, and protection against "harvest now, decrypt later" attacks.¶

Soundness is a different matter: it rests on the hardness of the discrete logarithm problem over the curves of Section 8, which Shor's algorithm solves efficiently on a quantum computer. These proofs MUST NOT be relied upon for post-quantum soundness. Implementations requiring post-quantum soundness SHOULD transition to alternative proof systems, e.g. MPC-in-the-Head ([GiacomelliMO16]), lattice-based ([AttemaCK21]), or code-based ([Stern93]) approaches. During migration, a hybrid AND composition of a classical-sound and a post-quantum-sound proof retains soundness if both underlying problems remain hard; unlike the free composition of linear relations described in Section 4.3, such composition across heterogeneous proof systems is not addressed in this specification, but examples may be found in the proof-of-concept implementation and in [BonehS23].¶

Appendix A. Imperative construction of a linear relation

The declarative notation of Section 4.3 assumes the shape of a relation -- its scalars, elements, and equations -- is known when the specification is written. Some relations are only fully known at run time (for instance, a range proof over a caller-supplied number of bits); Section 4.3's loop form already covers this by unrolling in the order the loop executes, but an implementation may instead prefer to build the LinearRelation incrementally. This appendix gives one such imperative construction API, informative only: it is one way to implement the compiler underlying Section 4.3 and Section 4.3, Paragraph 2, not a normative interface.¶

class LinearRelationBuilder:
    def allocate_scalars(self, n: int) -> list[int]
    def allocate_elements(self, n: int) -> list[int]
    def append_equation(self, lhs: int, rhs: list[(int, int)]) -> None
    def set_elements(self, elements: list[(int, Group)]) -> None
    def build(self) -> LinearRelation
¶

allocate_scalars(n)/allocate_elements(n) reserve n new scalar/element indices and return them. append_equation(lhs, rhs) appends one Equation (Section 4.2) with the given image index and terms. set_elements assigns concrete Group values to previously allocated element indices; every allocated element MUST be set before build() is called. build() returns the LinearRelation accumulated so far.¶

The Chaum-Pedersen relation of Section 4 is built this way as:¶

builder = LinearRelationBuilder(group)
[var_x] = builder.allocate_scalars(1)
[var_G, var_H, var_X, var_Y] = builder.allocate_elements(4)
builder.append_equation(var_X, [(var_x, var_G)])
builder.append_equation(var_Y, [(var_x, var_H)])
builder.set_elements([(var_G, G), (var_H, H), (var_X, X), (var_Y, Y)])
relation = builder.build()
